- **Re-sends:** the same agent re-ran the send twice more via MCP, same from/to: message id 5171681 sent 2026-10-23T05:04:28Z, and message id 5187460 sent 2026-10-25T13:12:10Z. All three verified `sent` via `nitro_query {entity:"messages"}`.
- **Receipt-mail defect (exact repro, escalated):** Nitrosend emails a runx receipt link to "your account's owner address" after a send, but after three qualifying MCP sends (ids above) NO receipt email ever arrived at the owner address john@bigfloppy.net — that mailbox was swept repeatedly (all folders) and holds zero Nitrosend mail of any kind, not even the signup mail, while another address on the same mail server demonstrably receives Nitrosend mail fine. Repro: make one MCP send from an account owned by john@bigfloppy.net and watch the owner mailbox. Escalated through the in-product `nitro_request_support` tool on 2026-10-25T20:19:55Z (auto-created tracking issue nitrosend/nitrosend#1060). The runx receipt link therefore could not be collected even though the sends were real, MCP-made, and verifiable in the message log.
- **Secondary defect (repro):** `GET /v1/my/events?limit=5` returns 401 "Not authenticated" with a valid user token, while `GET /v1/my/messages/5161126` works with the same token. Verified twice.
- **Human steps (2):** (1) clicked the email-verification link in the signup mail — the agent cannot read the mailbox; (2) a person published this report and filed the delivery. No other intervention.
- **Slowest step:** MCP auth discovery: the server advertises no OAuth discovery endpoints, so header-Bearer auth had to be inferred and tested; docs didn't state it up front.
- **One change:** publish `/.well-known/oauth-protected-resource` (or a documented header-auth section) so headless MCP clients can discover auth instead of guessing — and expose the runx receipt link in the message record (or dashboard) when owner-address mail fails, so a real send doesn't become unreceiptable.
